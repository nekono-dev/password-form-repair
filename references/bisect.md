# 切り分け手順（監査と表で直らなかった場合）

拡張機能の挙動は実機でしか分からないので、1回に1要因だけを変えて、利用者に試してもらう。依頼のたびに、**どのブラウザ・どのページで・何をして・何を貼り返してほしいか**を明記する（「貼り付けて」だけでは何を貼るのか伝わらない）。

## 1. 属性の実測

フォームを開いた状態（入力欄は未クリック）で、利用者のブラウザの開発者ツールのコンソールに、`scripts/dom-probe.js`の「1. 入力欄の一覧」と「2. 祖先とPassの印」を1つずつ貼ってもらい、出力を貼り返してもらう。

見るもの:
- 各欄の`ac`（実際のautocomplete）・`vis`（可視サイズ。`0x0`は見えていない）・`dlg`/`modal`（ダイアログ内か、モーダルか）・`form`（どの`<form>`に属するか）。
- `data-protonpass-*`の印が付いた要素。Passがどの要素をフォームとして扱ったかが分かる（`<main>`などに付いていれば、フォームの範囲を取り違えている）。

対象のフォームは、画面上の最初のパスワード欄を含む`<form>`。別のフォームを見るときは、ブロック先頭の`const S=null`を`const S='CSSセレクタ'`に書き換えてもらう。

## 2. イベント記録

同じファイルの「3. 自動入力の記録」を貼ってから、ユーザー名欄で候補を選んでもらい、出た行を全部貼り返してもらう。

- パスワード欄（`PASS`）にイベントが1つも来ない → Passがパスワードを入力しようとしていない。フォームの分類の問題（#4・#5・#7・#8を疑う）。
- イベントが来て値が消える → アプリの再描画が値を消している（制御入力のstateの初期化、`key`の変化による再マウントなど）。

## 3. 構成違いの並置テスト

```bash
node <このスキルのパス>/scripts/make-bisect-page.mjs <出力先>/pw-test.html
```

生成したページを静的に配信される場所（Vite・Astroなら`public/`）へ置き、検証環境へ反映する。利用者に、各ブロックを試して報告してもらう。

- ログインのブロック（A〜J）: ユーザー名欄で候補を選び、「両方入った／ユーザー名だけ／どちらも入らない」。
- 変更のブロック（K〜L）: 新しいパスワード欄で生成を使い、「生成値がどの欄に入ったか」。

まず基準Aが「両方入る」ことを確かめる。Aで入らなければ、ページ以前の問題（拡張機能の設定、対象URLのエントリの有無）。ブロックは`scripts/make-bisect-page.mjs`の`VARIANTS`を編集して増やす。基準から1回に1要因だけ変えたブロックにする。

## 4. 静的ページで通り、アプリで通らないとき

アプリの実DOMを写して比べる（`dom-probe.js`の「4. フォームを写す」）。元のフォームのすぐ下（祖先は同じ）と、ページ先頭（祖先なし）に静的な複製を置くので、どちらで入るかを試してもらう。

- 先頭の複製で入り、すぐ下の複製で入らない → 祖先・兄弟要素（同じ区画の別の欄、`form`属性の関連づけ）が分類を崩している（#7・#8）。
- どちらでも入らない → フォームの中身の問題。テストページのブロックと1要因ずつ突き合わせる。

複製をアプリ上に置いて試す場合、Passが付けた`protonpass-*`の要素・属性が複製に混ざり、結果が汚れる。毎回、再読み込みした直後に実行してもらう。

## 5. 後始末

切り分けが終わったら、テストページ（`pw-test*.html`）を**必ず削除**する。コミットせず、検証環境からも消す。分かった事実は、プロジェクトの設計書・作業記録に残す。表に無い新しい事実なら、このスキルの`references/findings.md`と表への追加を提案する。
